# Scenariusze testów aplikacji

Ten dokument jest mapą pokrycia wymagań automatycznymi scenariuszami testowymi. Każdy identyfikator wymagania FR/TR ma co najmniej jeden przypisany test automatyczny, jeśli można go wykonać w powtarzalnym środowisku testowym. Logika, którą można odizolować, musi mieć test jednostkowy. Test ręczny nie zastępuje testu automatycznego, który można uruchomić na emulatorze, fixture'ze lub w CI.

## Konwencje

- `U-FR-xx` / `U-TR-xx` — test jednostkowy logiki, walidacji, obliczeń lub transformacji.
- `I-FR-xx` / `I-TR-xx` — test integracyjny z bazą, emulatorem, systemem plików lub atrapą usługi.
- `E-FR-xx` / `E-TR-xx` — automatyczny test UI/E2E albo przepływu aplikacji desktopowej.
- `B-TR-xx` — automatyczny test buildu, konfiguracji lub artefaktu wydania.
- `M-FR-xx` / `M-TR-xx` — uzupełniający test ręczny. Wymagany tylko dla zachowań zależnych od prawdziwego dostawcy, systemu operacyjnego lub oceny wizualnej.
- Używaj deterministycznego zegara, syntetycznych danych i atrap sieci. Nie umieszczaj prawdziwych wyciągów, danych osobowych, tokenów ani sekretów w repozytorium.
- Testy integracyjne Firebase uruchamiaj na emulatorach. Testy nie mogą korzystać z produkcyjnego projektu ani prawdziwych kont.
- Test sprawdzający eksport musi analizować zawartość i uprawnienia pliku, nie tylko potwierdzać jego istnienie.

## Zasady odbioru testów

1. Każda pozycja z kolumny „Inny test automatyczny” musi wskazywać istniejący test w repozytorium lub zatwierdzony test platformowy CI; sam opis bez uruchamialnego testu nie oznacza pokrycia.
2. Każdy test jednostkowy należy uruchamiać szybko i bez sieci, z kontrolowanym zegarem oraz zależnościami. Logika biznesowa nie może wymagać Firebase ani prawdziwego API, aby dało się ją testować.
3. Testy integracyjne uruchamiaj na izolowanej bazie/emulatorze i czyść dane po każdym scenariuszu. Sprawdzaj także odmowę dostępu, nie tylko udane operacje.
4. Testy E2E obejmują najważniejsze drogi użytkownika i błędy widoczne w interfejsie. Nie zastępują testów jednostkowych reguł finansowych.
5. Testy ręczne oznaczone `M` są wymagane dodatkowo tam, gdzie automatyzacja nie może wiarygodnie odtworzyć prawdziwego systemu operacyjnego lub zewnętrznej usługi.
6. Przed wydaniem wygeneruj raport pokrycia wymagań: dla każdego FR/TR podaj wynik ostatniego wykonania testu, identyfikator testu i warstwę. Każdy brak automatyzacji uzasadnij i przypisz do testu ręcznego.
